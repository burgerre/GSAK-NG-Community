# Beiträge / Contributing

Makroideen und Beiträge können in Discussions vorgeschlagen werden. Der freigegebene Makrokatalog ist anfangs leer; neue Dateien werden erst nach individueller Prüfung und Freigabe aufgenommen.

## Deutsch

Du brauchst kein zusätzliches GSAK-NG-Konto. Zum öffentlichen Mitschreiben oder Vorschlagen einer Datei verwendest du GitHub. Du kennst GitHub noch nicht? Beschreibe deine Idee zuerst über das private Wunschformular. Dort werden keine Makrodateien hochgeladen; einen geeigneten Übermittlungsweg sprechen wir bei Bedarf separat ab. Keine Passwörter oder Zugangsschlüssel einsenden.

### Erst abstimmen

Vorhandene Diskussionen und Makros durchsuchen. Geplanten Beitrag in der Kategorie Makros beschreiben: Welches Problem löst er? Welche GSAK-NG-Version und Plattform nutzt du? Besteht bereits ein ähnlicher Beitrag? DE/EN mit [DE] bzw. [EN] im Titel kennzeichnen. Keine persönliche Kontaktadresse öffentlich erforderlich.

### Beitrag vorbereiten

- Makroname, kurze Beschreibung, Kategorie und öffentlicher Autorenname.
- Originalversion, Mindestversion wenn bekannt, Anleitung, Änderungen und bekannte Grenzen.
- Plattformunterstützung getrennt angeben: unbekannt, geplant, implementiert, getestet oder nicht unterstützt. Für Tests exakte Makro-/App-Version, Plattform und Ergebnis mit Nachweis nennen.
- Lizenztext und Recht zur Weitergabe/Änderung jeder fremden Datei, Abbildung oder Abhängigkeit belegen. Öffentliche Abrufbarkeit reicht nicht aus; alte GSAK-Makros nicht ohne geklärte Rechte kopieren.
- Beispieldaten bereinigen: keine privaten Cache-Koordinaten, Benutzerdaten, lokalen Pfade, Tokens, Kennwörter oder geschützten Anhänge.
- Verständliche Erklärung der Datei-/Datenbankänderungen, benötigten Netzverbindungen und sonstigen Voraussetzungen. Nutzer müssen Auswirkungen vor Ausführung einschätzen können.

Nach Abstimmung kann ein Fork mit Änderungsvorschlag (Pull Request) verwendet werden. Kein direkter Schreibzugriff auf den Hauptzweig ist dafür erforderlich. Der Ablagepfad wird vor Aufnahme eines Makros mit dem Maintainer abgestimmt. Beiträge werden nicht automatisch angenommen oder ausgeführt.

### Prüfung und Freigabe

Maintainer prüfen Rechte, Metadaten, Funktionsumfang und Testnachweise. Rückfragen und bekannte Lücken dokumentieren. Freigabe getrennt von Teststatus: «Community» bedeutet Herkunft, keine Prüfung; «experimentell» kennzeichnet belegte Einschränkungen; «geprüft» braucht einen konkreten Prüfumfang und Nachweis für diese Version. Keine pauschale Plattform- oder Sicherheitsgarantie.

Erst nach ausdrücklicher Freigabe erscheinen eine exakt versionierte Datei und ihr Katalogeintrag. Version, Commit, Dateigrösse und Hash nachvollziehbar speichern. Bestehende Releases nicht still ersetzen. Heruntergeladene Makros werden nicht automatisch ausgeführt; eine spätere App-Installation ist noch kein Teil dieses Starts.

## English

No separate GSAK-NG account is required. Use GitHub to post publicly or propose a file. If GitHub is unfamiliar, describe your idea through the private wish form first. That form does not accept macro uploads; arrange an appropriate transfer method separately if needed. Never send passwords or access keys.

Search existing macros and discussions before proposing a contribution in the Macros category. Describe the problem, app version, platform and any similar contribution. Use [DE] or [EN] title prefixes. Public contact details are not required.

Prepare the macro name, description, category, public author name, original version, known minimum app version, instructions, changelog and limitations. Describe platform support separately and provide exact versions, platform, results and evidence for any tests. Include the licence and redistribution rights for third-party files and images. Public visibility does not grant redistribution rights; do not copy old GSAK macros without permission. Remove private data and credentials from code, logs and examples. Explain file/database changes and network requirements.

After agreement, propose changes using a fork and pull request; direct write access is not needed. Agree exact paths with the maintainer before adding a macro. Contributions are not accepted or executed automatically. Maintainers review rights, metadata, scope and evidence, document gaps, and approve an exact release version separately. Community origin is not a test result; experimental limitations must be documented; reviewed status needs scoped evidence for the relevant version. No blanket compatibility or safety guarantee.

Approved releases keep an exact version, commit, file size and hash. Do not silently replace existing versions. Downloaded macros are not run automatically. Future app installation is outside the initial launch.
